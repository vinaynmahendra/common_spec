# Spec templates

Each spec uses one template (front matter `template`, or inherited from its parent). The JSON files are the source; the Markdown files are generated for reading.

| Template | Name | Used for |
|---|---|---|
| [`area`](area.md) | Area overview | The top-level areas (Multi-tenancy, Platform Packages, Infrastructure, Reporting and Analytics …) |
| [`package`](package.md) | Shared package | Authentication, Storage, Caching, Settings, Feature flags, Search, Data access, Notifications, Audit trail, Rules and Decision Engine, Human tasks, Workflow templates (interpreter), Data retention and legal hold, Calendars and deadline computation |
| [`security`](security.md) | Access and security control | Authorization (RBAC/ABAC), ethical walls, MFA and sessions, SSO, encryption utilities, input sanitisation, rate limiting |
| [`domain`](domain.md) | Domain module | Cases, Neutrals, Transcribers, Hearings, Documents, Invoices and vendor bills |
| [`workflow`](workflow.md) | Workflow / process | Case lifecycle flows, hearing scheduling and reminders, service of notices, eBundling, transcription and AI pipelines, data principal rights requests, dunning, tenant provisioning |
| [`rules`](rules.md) | Decision / rule set | Fees and cost schedules, tribunal size, deadlines and reminder policies, routing and allocation, eligibility checks, access policies expressed as rules |
| [`ui`](ui.md) | UI screen and user journey | Party / counsel portal, neutral workspace, secretariat console, tenant admin, transcriber workspace, onboarding flows |
| [`report`](report.md) | Operational report / analytics | Platform stats (case ageing, neutral and transcriber performance, documents), internal MIS, platform performance, AI usage analytics, client-wise analytics |
| [`regulatory`](regulatory.md) | Regulatory / aggregator submission | Regulator and aggregator submissions where a rule prescribes the recipient, format and deadline: ODR status reports to an MII (e.g. NSE for SEBI matters), MSME aggregator reporting, regulator returns where an obligation is confirmed (RBI, SEBI, IRDAI), event-driven statutory notifications (personal data breach notifications), and Annexure-style submissions |
| [`control`](control.md) | Compliance control | ISMS controls, privacy controls (DPDP / GDPR / PDPA), access reviews, data classification, vulnerability management, vendor / sub-processor management, ISO 27001 and SOC 2 evidence, incident response and breach notification, business continuity, consent management, AI governance (ISO 42001) |
| [`infra`](infra.md) | Infrastructure component | Compute and orchestration, Postgres, PgBouncer, Redis, Temporal cluster, networking, secrets and keys, backup and disaster recovery |
| [`integration`](integration.md) | Integration | Payment gateways, e-signature, KYC and sanctions providers, video conferencing, calendar, email / SMS providers, accounting (e.g. Odoo), regulator portals, public API and webhooks |
| [`standard`](standard.md) | Engineering standard | Monorepo layout, TypeScript and code conventions, environment management, frontend standards, CI/CD, migration strategy, testing strategy, documentation standards |
| [`observability`](observability.md) | Observability signal | Observability foundations, business events, performance, usage, security events, AI usage telemetry, alerting, uptime monitoring |
| [`ai`](ai.md) | AI capability | AI gateway, prompt management, RAG, guardrails, human-in-the-loop, AI cost controls, AI features in domains (summaries, drafting assistance, transcription), evals |
| [`billing`](billing.md) | Commercial / billing | Plans, entitlements and usage metering, invoicing and taxes, payment gateway flows, revenue reporting hooks, case fees and neutral / transcriber payouts |
| [`adr`](adr.md) | Decision record | Technology and architecture choices (tenant isolation, hosting, ORM, workflow engine, queue technology, orchestration) and open decisions awaiting a choice |
| [`design`](design.md) | Design note | Cross-cutting designs such as Separation of Concerns (Temporal), workflow engine selection, data residency and region routing, tenant context propagation, the reporting data pipeline, document storage and bundling |
| [`requirement`](requirement.md) | Requirement | Leaf statements under any capability: "Prisma Client extension sets tenant per transaction", "Automated tests prove one tenant cannot read another's rows" |
| [`plan`](plan.md) | Delivery plan | Order of implementation, phase plans, migration plans (e.g. moving existing CORD / TERES modules onto the new scaffolding) |
| [`api`](api.md) | API contract | One node per resource family or event family that other teams, tenants or third parties code against. Examples from our tree: the public Case API and Documents API under Public API and webhooks (9.4), the outbound webhook event catalogue (2.3.3), internal tRPC routers per persona (2.3.1), the tenant admin API (users, settings, branding), and the API error catalogue. Use Engineering standard for cross-cutting API rules (2.3.2 versioning, rate limiting, idempotency) and Integration for connections to a specific external provider. |
| [`datamodel`](datamodel.md) | Data model and schema | One node per schema area owned by a domain module or package. Examples from our tree: the Cases schema under Cases (6.1), the Hearings, Documents and Invoices schemas under their domain nodes, tenancy and identity tables under the Tenant model (3.1), the audit log tables under Audit trail (5.10), and the reference and seed data catalogue under Data access (5.13). The Domain module node describes the business model and lifecycle in business language; this node turns it into Postgres and Prisma. Cross-cutting rules (every table has tenant_id, RLS is forced) live in the Multi-tenancy security nodes and are applied, not restated, here. |
| [`frontend`](frontend.md) | Frontend architecture | One node per persona route group or app surface: party / counsel portal `(counsel)`, neutral workspace `(neutral)`, secretariat console `(secretariat)`, transcriber workspace `(transcriber)`, tenant admin `(tenant-admin)`, platform admin `(platform-admin)`, public and sign-in surfaces `(public)`. Also the app-level frontend node (Route groups per persona) that sets defaults every group inherits. Use the UI template for individual journeys and screens, Standard for repo-wide rules, Package for the design system library. |
| [`designsys`](designsys.md) | Design system foundations | UI / design system tokens and foundations (under 5.14 PKG-ui-design-system), Branding and theming (5.8.5), colour modes and dark mode, typography for multiple scripts, data-visualisation palettes for Reporting (12), and the print theme for awards, orders and eBundles. |
| [`component`](component.md) | UI component | Components in the shared UI package (5.14 PKG-ui-design-system): for example file upload dropzone, data table for the case list, date-time picker with time zones for the hearing scheduler, combobox party picker, modal dialog for consequential confirmations, case timeline, deadline badge, tenant switcher, document viewer. Not for full screens or journeys (use the UI screen and user journey template). |
| [`accessibility`](accessibility.md) | Accessibility conformance | Accessibility for a product surface or the platform as a whole: the platform-wide accessibility node (today 'Accessibility (WCAG 2.1 AA)'), party / counsel portal, neutral workspace and hearing room, secretariat console, tenant admin, generated documents and eBundles, accessible identity and KYC, conformance reports (ACR / VPAT) and the public accessibility statement. Not for a single screen's accessibility notes (those stay in the UI journey node) or for the test tooling standard (Accessibility testing). |
| [`content`](content.md) | Content design and UX writing | Platform voice and style guide, glossary and terminology governance, the error message catalogue, legal / declaration / consent text register, notification copy (email, SMS DLT templates, WhatsApp), plain-language guidance for unrepresented parties (SEBI ODR, MSME), privacy notice copy, content for a specific journey when its copy needs more than the UI node's Content section, and tenant terminology overrides. Not for the translation tooling and pipeline (I18N standards) or per-tenant language-pack mechanics (I18N Content package). |
| [`config`](config.md) | Settings catalogue | Settings catalogues per domain: security and identity, cases and workflows, notifications, integrations, branding, content and locale, AI, data retention and privacy, billing and plans, personal preferences, platform operations |
