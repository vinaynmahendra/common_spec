# 4.1 i18n

<!-- Generated layout: edit text between the markers; keep the markers and the front matter. -->

> string externalisation, translation workflow, RTL support

<!-- section:purpose -->
## Purpose and scope

Sets the rules for making every user-facing string translatable: where strings live, how messages are identified and written, how translations are produced and checked, and how layouts support right-to-left scripts. It applies to all apps, emails, SMS and WhatsApp templates, generated PDFs and API problem text. Formatting of dates, numbers and currency is in [[I18N-l10n]].

<!-- section:rules -->
## Rules

- **I18N-1** All user-facing text is referenced by message ID through `@nomology/i18n` (`t('cases.filing.submit.button')` on server and client). No literals in JSX, server actions' user messages, email or PDF templates.
- **I18N-2** Message IDs are `<domain>.<screen-or-feature>.<element>[.<variant>]`, lowercase with dots, stable for the life of the message. Changing meaning means a new ID; the old one is deleted.
- **I18N-3** Source catalogues are `packages/i18n/messages/en/<namespace>.json`, one namespace per domain or package; each message has a translator description (`@description`) and, where length matters, a max length.
- **I18N-4** Messages use ICU MessageFormat for variables, plurals and selects [R1]. No concatenation of translated fragments, no sentence built from parts, no plural logic in code.
- **I18N-5** Variables that hold user content are passed as values and rendered escaped; rich text uses tag placeholders (`<link>…</link>`) mapped to components, never raw HTML in messages.
- **I18N-6** Translations are produced in the translation management system (TMS) with the platform termbase ([[I18N-platform-glossary-and]]), screenshots and descriptions. Legal and procedural strings (namespace tag `legal`) need a qualified legal translator and approval per [[I18N-legal-declaration-and-consent]].
- **I18N-7** A release may include a locale only if that locale has 100% of messages in the namespaces used by the journeys enabled for it, with no stale translations (source changed after translation). Missing messages fall back to English with a logged warning, never to the message ID.
- **I18N-8** Pseudo-locales run in CI: `en-XA` (accented and 40% longer) and `ar-XB` (right-to-left pseudo). Journey e2e tests run in both and fail on untranslated literals, clipped text or broken layout. Short strings may expand much more than 40% in real translation, so UI components must wrap rather than truncate [R2].
- **I18N-9** Layout uses CSS logical properties (`margin-inline-start`, `padding-block`), `dir` is set on `<html>` from the locale and on elements whose content direction differs (for example a Latin case number inside Urdu text) [R3]. Icons with direction meaning (back, next) mirror in RTL; logos, media controls and charts do not.
- **I18N-10** The locale is chosen by: user preference, then tenant default, then `Accept-Language` among the tenant's enabled locales, then English. The choice is stored on the user profile and used for notifications ([[PKG-notification-preferences]]).
- **I18N-11** `lang` is set on `<html>` and on any part in a different language (for example an English legal text shown alongside a Hindi explanation).
- **I18N-12** Tenant terminology overrides are applied through the message layer (tenant language packs, [[I18N-content]]), not by editing source messages.

<!-- section:rationale -->
## Rationale

- **I18N-4** Plural rules differ by language (Hindi, Chinese and English differ), and word order makes concatenation untranslatable.
- **I18N-7** A half-translated legal journey can mislead a party about a deadline; falling back to English is safer than showing a key or mixing meanings.
- **I18N-9** Urdu is among the languages listed in the Eighth Schedule of the Constitution of India, which matters for Indian notices, so RTL support is a real requirement, not a hypothetical one.

<!-- section:tooling -->
## Tooling and configuration

- `next-intl` (proposed) for App Router, wrapped by `@nomology/i18n` so the library can be replaced; `@formatjs/cli` for extraction and ICU validation.
- ESLint `react/jsx-no-literals` (with allow-list for punctuation) and custom `no-concat-messages` rule.
- Stylelint with `stylelint-use-logical` (or equivalent) to ban physical direction properties.
- TMS (to be selected) with termbase, translation memory and GitHub sync; CI job `i18n-extract` checks catalogue drift and ICU syntax.

<!-- section:enforcement -->
## Enforcement

| Rule | Enforcement |
|---|---|
| I18N-1, I18N-4, I18N-5 | ESLint (required); ICU syntax validation in `i18n-extract` |
| I18N-2, I18N-3 | Catalogue schema check (ID pattern, description present) |
| I18N-6 | TMS workflow states; `legal`-tagged strings cannot be marked approved without the legal reviewer role |
| I18N-7 | Release gate per tenant locale (coverage and staleness report) |
| I18N-8 | Pseudo-locale e2e projects in Playwright (required in staging) |
| I18N-9 | Stylelint (required); RTL visual snapshots |
| I18N-10, I18N-11 | Unit tests of locale negotiation; axe `html-has-lang` and `valid-lang` |

<!-- section:examples -->
## Examples

Good:

```json
"cases.list.summary": {
  "message": "{count, plural, =0 {No open cases} one {# open case} other {# open cases}}",
  "@description": "Heading above the case list. count = number of open cases visible to the user."
}
```

Bad: `` `${count} open case${count === 1 ? '' : 's'}` `` in a component.

<!-- section:exceptions -->
## Exceptions

Proper nouns (tenant names, product names CORD and TERES), case reference numbers and code samples in developer docs are not translated. Other exceptions follow [[FND-governance#exceptions]].

<!-- checks -->
## Template checks

<!-- check:enforcement -->
### Enforcement

Literals, concatenation, ICU syntax, catalogue structure and physical CSS properties are lint- or CI-enforced; locale completeness is a release gate; legal translation approval is enforced by TMS roles.

<!-- check:guardrails -->
### Security, tenancy and privacy guardrails

Message variables are escaped (I18N-5) so tenant or party text cannot inject markup; legal strings are locked to legal translators and approvers; accessibility language marking (I18N-11) supports WCAG 3.1.1 and 3.1.2.

<!-- check:onboarding -->
### Onboarding and usability

`pnpm i18n:extract` updates catalogues; lint messages explain how to replace a literal with `t()`; pseudo-locale can be switched on locally with `?locale=en-XA`.

<!-- check:measurement -->
### Adoption measurement

Per locale: message coverage and stale count; literal-string lint suppressions (target 0); RTL snapshot failures.

<!-- check:ownership -->
### Ownership and change

Owner: frontend platform lead; content design owns message descriptions and termbase.
