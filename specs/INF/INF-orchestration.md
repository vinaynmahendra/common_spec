# 14.3 Orchestration

<!-- Generated layout: edit text between the markers; keep the markers and the front matter. -->

> ECS on Fargate per region (Azure Container Apps where required): clusters, services, deployments, service discovery and autoscaling mechanics

<!-- section:purpose -->
## Purpose and responsibilities

Runs the workloads defined in [[INF-compute]]: clusters, services, task definitions, deployment strategy, service discovery and autoscaling. Decided by [[ADR-container-orchestration]]: **Amazon ECS on Fargate** per region; **Azure Container Apps** as the equivalent where a region or client requires Azure.

Depended on by: every application workload, [[INF-temporal]] (Temporal server services run here), [[INF-pgbouncer]] (AWS), [[DEP-blue-green-canary-releases]].

<!-- section:topology -->
## Topology per region

One ECS cluster per region and environment; Fargate capacity providers; services spread over three availability zones.

| ECS service | Load balancer | Discovery | Notes |
|---|---|---|---|
| `web` | Internal target of public ALB (behind CDN) | — | Rolling with circuit breaker, or blue/green via CodeDeploy for canary |
| `worker-jobs` | None | — | Rolling |
| `worker-temporal-<queue>` | None | — | Rolling; Worker Versioning handles code changes ([[WF-separation-of-concerns-temporal]]) |
| `pgbouncer` | Internal NLB (TCP 6432) | `pgbouncer.<region>.internal` | Rolling one task at a time |
| `temporal-frontend`, `-history`, `-matching`, `-worker` | Internal NLB for frontend (gRPC 7233) | ECS Service Connect for internal membership | See [[INF-temporal]] |
| `otel-collector` | Internal NLB (OTLP 4317/4318); public path via ALB for browser RUM | — | [[OBS-frontend-real-user-monitoring]] |

**AWS to Azure mapping**

| Concern | AWS (default) | Azure Container Apps |
|---|---|---|
| Cluster | ECS cluster, Fargate | Container Apps environment (workload profiles, VNet-injected, internal) |
| Service | ECS service + task definition | Container App + revision |
| Batch / one-off | ECS RunTask (`migrate`) | Container Apps Job |
| Autoscaling | Application Auto Scaling on CloudWatch metrics | KEDA scale rules (HTTP, CPU, Redis list / custom metric) |
| Canary | CodeDeploy blue/green | Revision traffic splitting |
| Service discovery | Service Connect / Cloud Map | Built-in internal DNS |
| Secrets | Task definition `secrets` from Secrets Manager | Key Vault references with managed identity |
| Pooler | PgBouncer service | Flexible Server built-in PgBouncer |

<!-- section:sizing -->
## Sizing and scaling

Starting counts and triggers are in [[INF-compute#sizing]]. ECS limits to watch: tasks per service (default quota is high enough), Fargate vCPU quota per region (request increase to 400 vCPU in ap-south-1 before go-live), ALB targets. Azure: Container Apps environment core quota per subscription; request increases before onboarding a client.

<!-- section:config -->
## Configuration baseline

- Deployment: `minimumHealthyPercent=100`, `maximumPercent=200`, deployment circuit breaker with rollback on; health check grace 60 s for `web`.
- Task definitions are generated by the `ecs-service` module from one typed input (image digest, size, env, secrets, ports, health check); applications never write raw task definitions.
- `stopTimeout` 60 s (workers) / 35 s (web) to allow graceful drain ([[INF-compute#config]]).
- Logging: `awsfirelens` or OTLP from the app to the regional collector; container stdout goes to a regional CloudWatch log group as a fallback with 14-day retention.
- Container Insights enabled for task-level metrics.
- Service auto scaling: target tracking on CPU and request count for `web`; step scaling on custom backlog metrics for workers.

<!-- section:resilience -->
## High availability and DR

- AZ loss: services keep running on remaining two AZs; minimum task counts sized so remaining capacity carries 100% of normal load at higher CPU (target CPU 60% leaves room).
- Region loss: orchestration is rebuilt from IaC in the DR region (where one is approved); see [[INF-backup-and-disaster-recovery]].
- Control plane outage (ECS API): running tasks continue; deploys and scaling pause. Runbook says: freeze deploys, do not delete services.
- No RPO; RTO for redeploying all services into an empty cluster: under 30 minutes.

<!-- section:security -->
## Security

- Tasks in private subnets; security groups per service allow only the listed callers (for example `pgbouncer` accepts 6432 only from `web`, worker and `migrate` security groups).
- Task execution role (pull image, read secrets) is separate from the task role (application permissions).
- ECS Exec disabled in production; break-glass enables it on one task for a time-bound session that is recorded.
- Azure: Container Apps environment is internal-only; ingress through Front Door / Application Gateway with WAF; managed identities per app.

<!-- section:operations -->
## Runbook

- Deploy, rollback and canary steps: [[DEP-blue-green-canary-releases]].
- Migration task runs before `web` rollout and must finish before the new revision receives traffic.
- Pause a worker class during an incident: set desired count to 0 for that service (BullMQ jobs stay in Redis; Temporal tasks stay in the task queue).
- Drain an AZ: update the capacity provider strategy; tasks reschedule.

<!-- section:observability -->
## Monitoring and alerts

- Service-level: running vs desired tasks, deployment state, circuit-breaker rollbacks (ticket and chat), task stop reasons (OOM, health check failures).
- Alert: `web` running tasks below minimum for 5 minutes → page; any rollback by circuit breaker → chat and ticket.
- Events from ECS (task state changes) forwarded to the regional collector for correlation with deploys.

## Template checks

<!-- check:security -->
### Security

Separate execution and task roles, private subnets, per-service security groups listing exact callers, ECS Exec disabled in production except break-glass, and managed identities with Key Vault references on Azure.

<!-- check:isolation -->
### Tenant isolation and noisy neighbours

One cluster per region and environment; no cross-region services. Heavy tenant workloads are isolated by separate services per Temporal task queue so they scale independently and cannot exhaust `web` capacity.

<!-- check:iac -->
### Infrastructure as code and change control

ECS clusters, services and task definitions come only from the `ecs-service` / `ecs-cluster` modules in [[INF-cloud-and-iac]]; image digest is the only value CI changes per deploy. Azure uses the `container-app` module with the same inputs. No console edits; drift detection covers services and task definitions.

<!-- check:lifecycle -->
### Operations and lifecycle

Fargate platform versions are managed by AWS; we pin `LATEST` for Linux only after staging validation. The runbook covers deploy, rollback, pausing worker classes and AZ drain. Azure Container Apps runtime updates are managed by Microsoft and announced; we track them in the change calendar.
