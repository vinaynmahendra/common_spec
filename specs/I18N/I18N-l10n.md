# 4.2 l10n

<!-- Generated layout: edit text between the markers; keep the markers and the front matter. -->

> locale-aware dates, numbers, currency, time zones

<!-- section:purpose -->
## Purpose and scope

Defines how values are formatted and entered for each locale and time zone: dates, times, deadlines, numbers, currency, names, addresses and phone numbers. It covers display and input, not deadline computation, which is owned by [[PKG-calendars-and-deadline]].

<!-- section:rules -->
## Rules

**Storage**
- **L10N-1** Instants are stored as `timestamptz` (UTC); calendar dates without time (for example a date of birth or award date as written) as `date`; each case stores its seat time zone as an IANA zone ID (`Asia/Kolkata`, `Asia/Singapore`, `Asia/Hong_Kong`, `America/New_York`).
- **L10N-2** Money is stored as an integer in the minor unit with an ISO 4217 currency code (`INR`, `SGD`, `USD`, `HKD`); no floats.

**Display**
- **L10N-3** All formatting uses `@nomology/i18n/format` wrappers over `Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.RelativeTimeFormat`, `Intl.ListFormat` and `Intl.PluralRules`, backed by CLDR data [R1]. No manual formatting, no `toLocaleString` calls outside the wrappers.
- **L10N-4** Dates are shown with the month as a word or abbreviation ("14 Nov 2026" in `en-IN`/`en-SG`, "Nov 14, 2026" in `en-US`), never as ambiguous numeric dates like 11/12/2026.
- **L10N-5** Deadlines are rendered only through the `Deadline` component: date, time, time zone abbreviation and remaining time, in the seat time zone; if the viewer's time zone differs, the local equivalent is shown as well ("Due 17:00 HKT, 14 Nov 2026 — 14:30 IST for you"). The time zone used for the legal effect is always stated.
- **L10N-6** Times use the locale's 12- or 24-hour convention; hearing schedules always include the time zone.
- **L10N-7** Numbers follow locale grouping; `en-IN` uses Indian grouping (for example 1,00,000) as CLDR defines it. Currency is shown with code or symbol per locale; where several currencies could appear on one page (invoices, fee schedules), the ISO code is shown.
- **L10N-8** Server components format with the user's locale and time zone from the profile (fallback: tenant default), and the same values are passed to client components to avoid hydration mismatches.

**Input**
- **L10N-9** Date and time inputs use the shared picker ([[PKG-date-and-time-picker-with]]) and make the time zone of the entered value explicit. Typed dates accept the locale format and ISO 8601.
- **L10N-10** Names are one `fullName` field plus an optional `preferredName`; no forced first/last split. All name and address fields accept any Unicode script and are stored NFC-normalised.
- **L10N-11** Phone numbers are stored in E.164 and validated with libphonenumber metadata; display uses the national format for the user's region.
- **L10N-12** Addresses are free-form lines plus country (ISO 3166-1 alpha-2) and optional postal code validated per country where a rule exists.
- **L10N-13** Number inputs accept the locale's decimal separator and convert to canonical values on the server; amounts are never parsed in the browser alone.

<!-- section:rationale -->
## Rationale

- **L10N-5** A party in India, counsel in Singapore and an arbitrator in the US read the same deadline. Saying which time zone governs prevents missed filings, the most damaging localisation failure on this platform.
- **L10N-4** 11/12/2026 means different dates in the US and India.
- **L10N-10** Many names in India and elsewhere do not fit a first/last pattern; a forced split produces wrong notices and identity mismatches with KYC.

<!-- section:tooling -->
## Tooling and configuration

`@nomology/i18n/format` (formatters and `Deadline`, `Money`, `DateTime` components), `@internationalized/date` or the Temporal polyfill for zone-aware arithmetic in display code (proposed), `libphonenumber-js`, CLDR data via the runtime's Intl (Node.js full ICU).

<!-- section:enforcement -->
## Enforcement

| Rule | Enforcement |
|---|---|
| L10N-1, L10N-2 | Prisma schema lint: `DateTime` fields must be `@db.Timestamptz`; money fields must be `Int`/`BigInt` with a sibling currency field |
| L10N-3, L10N-4 | ESLint `no-locale-format` custom rule; unit tests of the wrappers per launch locale |
| L10N-5 | ESLint rule: fields named `*dueAt` / `*deadline*` may only be rendered via `Deadline` |
| L10N-8 | E2E test asserting no hydration warnings in each locale |
| L10N-10 to L10N-12 | Zod schemas in `@nomology/api-contracts` shared by forms and APIs |

<!-- section:examples -->
## Examples

Good: `<Deadline at={filing.dueAt} seatTimeZone={case.seatTimeZone} />` renders "Due by 17:00 IST, Fri 14 Nov 2026 (6 days left)".

Bad: `new Date(dueAt).toLocaleDateString()` — uses the server's locale and zone, and drops the time.

<!-- section:exceptions -->
## Exceptions

Machine-readable exports (CSV for aggregators, regulator reports) use ISO 8601 and canonical numbers regardless of locale, as defined by the report template.

## Template checks

<!-- check:enforcement -->
### Enforcement

Schema lint, custom ESLint rules for formatting and deadline rendering, shared Zod schemas and per-locale unit and e2e tests.

<!-- check:guardrails -->
### Security, tenancy and privacy guardrails

Deadlines always state the governing time zone (legal correctness); money in integer minor units avoids rounding errors in fees and invoices; names in any script avoid exclusion and identity mismatches.

<!-- check:onboarding -->
### Onboarding and usability

Engineers use three components (`Deadline`, `Money`, `DateTime`) and the format wrappers; lint tells them which to use.

### Ownership and change
